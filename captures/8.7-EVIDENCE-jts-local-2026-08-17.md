## Findings (finding-only; nothing filed)

**F1 — `jasper-active-speaker commission-ramp status` is permanently broken on
any box that has ever armed a driver.** `jasper/cli/active_speaker.py`
`_cmd_commission_ramp_status`:

```python
target = commission.get("target") or {}
group  = str(target.get("speaker_group_id") or ramp.get("speaker_group_id") or "").strip()
...
if group:
    topology = load_output_topology_strict(args.topology)   # ← line 1338
```

The `status` subparser registers only `-h` and `--json` — no `--topology` — so
`args.topology` raises whenever `group` is non-empty:

```
AttributeError: 'Namespace' object has no attribute 'topology'
  File "/opt/jasper/jasper/cli/active_speaker.py", line 1338, in _cmd_commission_ramp_status
```

**Correcting my own first reading of this**, which was "it only breaks
mid-ramp". `commission_load.target` **survives a rollback**. Verified after
everything was rolled back and the ramp state reset to base —
`{"status":"rolled_back","loaded":false,"target":{"role":"woofer",
"speaker_group_id":"left",…}}` — and `status` still crashes. It succeeded
exactly once this session: the very first invocation, on a box whose `target`
was still `{}` because no driver had ever been armed. So the verb works only on
a never-armed box and is dead from the first arm onward, not just during a
ramp. Reproduced four times, with that first success as the control.
Per `--help`, `commission-load` and `commission-ramp step` *do* register
`--topology`; `commission-ramp status`, `commission-ramp ack`,
`commission-ramp abort`, and `commission-rollback` do not — but `status` is the
only one of those four whose handler reads `args.topology`.

**F2 — `/state` truncates the playback level readout to 2 channels on a
4-output roleful box.** `jasper/control/state_aggregate.py:902`:

```python
def _round_pair(pair): return [_round_db(pair[0]), _round_db(pair[1])]
```

CamillaDSP returns four values on this box; `/state.audio.playback_rms_dbfs`
and `playback_peak_dbfs` publish two. Outputs 2 and 3 — the entire right
speaker — are never represented. Concretely, during the woofer ramp the live
websocket read `[-105.81, -1000.0, -105.81, -1000.0]` while `/state` could only
ever surface the first two. The dashboard therefore cannot show per-driver
level during commissioning on an active-crossover box.

**F3 — `commission-rollback` leaves the ramp's `pending` step behind.**
After `POST /active-speaker/commission-rollback` the graph was back on the
anchor and `commission_load.status=rolled_back`, but the ramp state file still
read:

```
{"speaker_group_id":"left","confirmed_roles":["woofer","tweeter"],
 "pending":{"gain_db":-80.0,"role":"woofer","playback_id":"4af2a9b7…"},
 "last_action":"step"}
```

Only `ack` and `abort` clear `pending`; a bare rollback does not. The next arm
calls `clear_pending_ramp_step` and `_pending_step_still_current` guards
staleness, so this is a consistency wart rather than a safety hole — but a
surface reading the ramp file between a rollback and the next arm will show a
pending audible step that no longer exists. Cleared here by a following
`abort`. Low severity.

**F4 — the safe-playback TTL is 120 s and the expiry is silent until the ACK.**
`safe_playback.DEFAULT_ARM_TTL_SEC = 120`. An operator who steps, walks to the
speaker, listens, and comes back gets `status="expired"` and must redo the
step. Correct fail-safe direction; worth knowing before an on-ear pass, because
on a real speaker the human round trip is exactly the thing that takes minutes.
Not a defect — recorded so the jts3 audible pass is not surprised by it.
