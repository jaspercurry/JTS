# TTS Playout Path Audit — Python socket write → DAC

Scope covered: `jasper/audio_io.py`, `jasper/voice/turn_playback.py`, `jasper/assistant_loudness.py`, `jasper/voice_daemon.py` (duck/telemetry call sites), `jasper/wake_events.py`, `rust/jasper-fanin/src/{tts,mixer,mixer/dsp,playout,loudness}.rs`, `rust/jasper-tts-protocol/src/{lib,loudness}.rs`, `rust/jasper-outputd/src/{tts,alsa_backend,config}.rs`, `jasper/camilla_config_contract.py`, `jasper/fanin_coupling.py`, `jasper/sound/camilla_yaml.py`, `deploy/camilladsp/outputd-cutover.yml`, `jasper/audio_hardware/dac.py`, `jasper/correction/fir_runtime.py`, `docs/adr/0004-*`.

**Approximate steady-state pipeline latency, socket-write-accepted → DAC** (typical hardware, no room correction): roughly **13-25 ms**, dominated by the mixer period (≤5.3 ms) and the DAC hardware buffer (5.3-64 ms depending on whether the box has a characterized `LatencyFloor`). This is an estimate assembled from the constants above, not a measurement. **This entire budget is dwarfed by the ~100 ms telemetry-observer stall in Finding F1**, and by the upstream STT/LLM/TTS-provider network latency this path doesn't touch at all.

**Already minimal / no meaningful change recommended:**
- The loudness/gain-decision path (no lookahead into the current segment's audio — decided instantly at `SEGMENT_START` from pre-computed state).
- Ducking (`program_duck_gain`) — TTS is structurally immune to the duck ramp; it mixes in after the duck is applied to the program lane only.
- `_OUTPUTD_PACE_AHEAD_SEC` — correctly scoped to prevent overflow of fan-in's 2 s pending budget; does not touch first-audible at all.
- CamillaDSP's ring-crossing chunk/target-level pair (128/128/1) — already at the floor the ring's ALSA geometry can serve (`resolve_camilla_latency_for_devices`, `camilla_config_contract.py:350-412`); tightening further would need a wider ring, which is a much larger structural change.
- Segment-start/end handshake — already deduped to once-per-logical-segment.

## 3. Code health of `tts.rs` (fan-in, 3,464 lines)

**Responsibility map** (non-test code is lines 1-1633, 47% of the file):
- Protocol *parsing* is not here — it's imported from `jasper_tts_protocol` (`TtsCommand`, `read_command`, `command_name`, line 35-37). `tts.rs` owns the **consumer** side.
- Telemetry/metrics packing: `TtsMetrics` struct + `Default` + accessors + seqlock pack/unpack helpers — lines 76-482 and 1525-1603 (~400 lines). This is largely mechanical `AtomicI64`/`AtomicU64` pack/unpack boilerplate for crossing the mixer-thread→STATUS-thread boundary via a seqlock (justified by the threading model, but very manual/hand-written; a macro or generic wrapper could shrink this considerably).
- Mixing/queueing engine (`TtsMixer`, `QueuedAudioBlock`, segment lifecycle, ducking-gain selection, assistant-reference completion): lines 505-1152 — the actual audio-path logic.
- A private `GainRamp` (lines 1221-1271, ~50 lines) — **see Finding F2**, this is a byte-for-byte duplicate of the shared `jasper_tts_protocol::loudness::GainRamp` (`loudness.rs:916-992`) that `jasper-outputd` already uses (`assistant_source.rs:33,73,128`) but fan-in's own `tts.rs` does not.
- Socket transport plumbing (accept thread, per-client thread, command/flush queueing, backpressure): lines 1273-1455 (~180 lines) — this is the code `jasper-outputd/src/tts.rs`'s own header explicitly calls "ported from fanin" (line 226), i.e. **acknowledged, non-shared duplication** of transport code across the two crates (the *wire parsing* is shared via `jasper-tts-protocol`; the *server loop* is not).
- Tests: **lines 1634-3464, 1,831 lines = 53% of the file.** A large, recurring source of bulk is per-test config literals repeating `program_duck_db: -25.0, cue_duck_db: -6.0` verbatim dozens of times (e.g. lines 1796-3025+) — a builder/default-with-overrides helper would cut this considerably without losing coverage.
- Comments: 310 lines file-wide; **152 of 1,550 non-blank lines in the non-test section (~9.8%)** are comments — the codebase's normal dense "why"-comment style (ADR-referencing, contract-explaining), not narration.

**Verdict**: 3,464 lines is not unreasonable for what it does (protocol consumer + a from-scratch mixing/loudness/ledger engine + telemetry + its own test suite), but over half is tests and the metrics-packing section is disproportionately large relative to the logic it carries. The one clear, fixable defect is the duplicated `GainRamp` (Finding F2) — everything else is either justified by the threading/architecture split or a minor test-boilerplate cleanup opportunity, not a real problem.

**`loudness.rs` (2,144 lines, shared crate):**
- Non-test: 1,153 lines (54%); tests: 991 lines (46%, `#[cfg(test)] mod tests` at line 1154).
- Comments in non-test section: 179/1,075 non-blank lines = **~16.7%** — noticeably denser prose than `tts.rs`, consistent with this file carrying the actual BS.1770 K-weighting/loudness-decision algebra that needs the extra explanation (documented, load-bearing math, not narration).
- Well-scoped single responsibility: K-weighting biquads, rolling LUFS windows, `AssistantLoudness`/`decide_gain`, the shared `GainRamp`, and the `TtsLoudnessSnapshot` JSON renderer shared verbatim by both daemons. No obvious bloat.

## 4. Duplicated concerns

- **F2 (Rust/Rust, confirmed via direct source comparison): `GainRamp` is defined twice.** `rust/jasper-tts-protocol/src/loudness.rs:916-992` is the "extraction of fan-in's private ramp" (its own doc comment says so) so outputd's post-DSP mix loop (`jasper-outputd/src/assistant_source.rs:33,73,128,313`) could share it. But `rust/jasper-fanin/src/tts.rs:1221-1271` still carries the pre-extraction private copy — field-for-field, method-for-method identical (`initialized`/`current_linear`/`target_linear`/`step_linear`/`remaining_frames`/`target_db`; `force_silent`/`retarget`/`next_frame`) — and fan-in's `TtsMixer` uses its own local one (`tts.rs:526,573,1149,2419`) rather than the shared import it already pulls other symbols from (`crate::loudness::{...}`, line 28-32, which does **not** list `GainRamp`). This is the extraction that never finished landing on the fan-in side. Fix: delete `tts.rs:1221-1271`, add `GainRamp` to the existing `crate::loudness::{...}` import list. Trivial, safe (`crate::loudness` is a pure re-export shim, `rust/jasper-fanin/src/loudness.rs:1-11`).
- **Socket-transport plumbing, acknowledged but real:** `spawn_tts_server`/`spawn_tts_client`/`handle_tts_client`/`queue_flush`/`try_enqueue_tts_command`/`enqueue_reliable_tts_command` (`jasper-fanin/src/tts.rs:1273-1451`, ~180 lines) is structurally mirrored by `jasper-outputd/src/tts.rs:229-411` (its own header literally says "ported from fanin," line 226). The wire *vocabulary* is shared (`jasper_tts_protocol`); the accept-loop/backpressure *code* is not. A shared generic transport module in `jasper-tts-protocol` is a plausible consolidation (M complexity — the two daemons' `QueuedTtsCommand`/`FlushSummary` types differ), but this is a known, documented tradeoff (the file explicitly separates "what is NOT duplicated: the engine"), not an oversight — lower priority than F2.
- **Gain/loudness decision itself is *not* duplicated** between Python and Rust in the way the prompt worries about: Python's `assistant_loudness.py` computes a **profile update** from the *previous* turn's audio (post-hoc, backgrounded via `_schedule_assistant_source_profile_save`, `audio_io.py:1800-1839`, explicitly to keep it off the critical path — "awaited inline here it blocked the loop for ~0.7s per second of reply"), while Rust's `loudness.rs::decide_gain` makes the **live per-segment gain decision** for the *current* turn using that persisted profile plus live volume/duck state. These are two halves of one pipeline, not two competing implementations of the same decision — no drift risk found here.
- **Pacing is computed in exactly one place** (Python `_OUTPUTD_PACE_AHEAD_SEC`); Rust enforces its own independent, unrelated bound (`DEFAULT_MAX_PENDING_FRAMES`, 2 s) as a hard drop-on-overflow backstop rather than a second pacing computation. `tests/test_tts_ipc_pacing.py` (per the comment at `audio_io.py:719-720`) pins the two constants against each other so they can't silently drift — this is the *correct* pattern, not duplication.
- **Minor:** the unconditional per-chunk `GAIN` resend (`audio_io.py:1681-1682`) duplicates work the adapter's own `set_gain_db` already does correctly when called from outside the write path (base class dedupes via `if clamped == self._gain_db: return`, `audio_io.py:517-519`) — negligible cost, listed for completeness under item 2.

## 5. Observability

**What exists today:**
- Python: `tts_wire.resolved` (once, at construction), `tts_fanin.adapter_timeout`/`reconnect`/`control_retry` (fault paths), a **slow-write WARN** comparing wall-clock write time to expected chunk duration (`audio_io.py:1748-1758`, `write_ms > chunk_ms + 100`) — the closest existing thing to a per-write latency check, but it only fires above threshold and isn't logged routinely. `take_paced_sec()` surfaces cumulative pacing-sleep time once per turn to the voice daemon's end-of-turn accounting line.
- Rust: `event=fanin.tts_flush` (with `flushed_frames`, `segments`, `max_audio_played_ms`), `event=fanin.assistant_loudness` (full gain-decision dump per segment start), `event=fanin.program_duck`, `event=fanin.tts_command_dropped`/`tts_command_backpressure` (queue-full drops), `event=fanin.tts_wire_width_mismatch`. `TtsMetrics` exposes `pending_frames`/`max_pending_frames`/`protocol_errors`/`dropped_commands`/`dropped_audio_frames`/`flush_requests`/`flushed_frames` plus the full loudness snapshot, presumably surfaced via a STATUS/`/state`-style endpoint (`render_assistant_loudness`, shared renderer in `jasper-tts-protocol/src/loudness.rs:744-895`).
- `jasper-outputd`'s ALSA backend counts `content_xrun_count`/`dac_xrun_count` (and per-child counts for composite sinks) — real underrun observability exists on the DAC-write side (`alsa_backend.rs:164-181,850-851`).

**What does *not* exist:** a per-turn "first audible byte" timestamp anywhere in the chain. The wake-event funnel (`jasper/wake_events.py:93-103`) already records `ts_response_started` — the moment the **provider's** first PCM chunk reaches the daemon (before local playout) — but nothing records when that audio actually reached the ring/DAC. **It could be emitted from one place cheaply**: `_write_segment`'s existing `write_start = time.monotonic()` (`audio_io.py:1678`) already brackets the socket write; a one-time (`response_started`-gated) log line there, or a corresponding first-write timestamp captured in `TtsMixer::mix_period` the first time a segment's first sample is popped (it already tracks `segment_serial`/`completes_assistant_reference` per segment, so "first sample mixed" is a trivial addition), would give a true local-playout-latency number without new machinery — it would just need wiring to the existing wake-event funnel's `ts_response_started` baseline for a real end-to-end "provider chunk → speaker" delta.

## 6. What is genuinely good

- **No hidden lookahead anywhere in the loudness/ducking/mixing critical path.** The gain decision, the duck mechanism (TTS mixed strictly after the duck, never gated on its ramp), and the TTS's own gain ramp (snaps instantly on first sample) were all verified line-by-line and none of them delay first audible.
- **Ring/CamillaDSP geometry is already tuned to the practical floor**: 128-frame ring slots end-to-end, CamillaDSP's `chunksize`/`target_level` clamped to exactly what the ring's ALSA `avail_min` constraint allows (`resolve_camilla_latency_for_devices`), with a documented, tested (`test_ring_reemit_carries_the_certified_ring_chunk_and_target`) rationale for why it isn't tighter.
- **Pacing and drop policy are correctly separated and cross-pinned**: Python's soft pace-ahead watermark (1.2 s) and Rust's hard drop threshold (2 s) are independently enforced but pinned against each other by a dedicated test, exactly the pattern this codebase's own doctrine asks for.
- **Expensive per-reply loudness measurement is correctly kept off the hot path** (`_schedule_assistant_source_profile_save`, explicit comment naming the 0.7 s/s cost it avoids by backgrounding).
- **DAC hardware buffering is a one-time startup cost, not a per-turn stall** — the daemon primes and continuously writes silence, so ALSA's `start_threshold` behavior never re-triggers per utterance.
- The `GainRamp`/pacing constants all carry load-bearing "why" comments with concrete incident references (e.g. the pace-ahead comment cites `event=fanin.tts_command_dropped, observed on JTS3 2026-06-11`) rather than speculative guards — matches AGENTS.md's "fix forward after a real incident" doctrine.
