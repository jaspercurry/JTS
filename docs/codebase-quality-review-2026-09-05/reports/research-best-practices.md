# Structure and quality reference for a mid-size, AI-agent-built polyglot codebase

Opinionated, not a survey. Written for: Python (~400k LOC) + Rust (~60k) + C + bash/systemd,
~900 test files, one owner, built almost entirely by AI coding agents. Where a claim is
folklore (widely repeated, weakly evidenced) it is labeled as such.

---

## 1. Structure

### Package-by-feature vs. package-by-layer
**Verdict: package-by-feature at the top level, layered only inside a feature if the feature is genuinely complex.** Package-by-layer (`controllers/`, `services/`, `models/`) forces almost everything to be public across layer boundaries and scatters one concern across N directories; package-by-feature groups a capability's code, tests, and (where applicable) types together, maximizing cohesion and letting internals stay private. This is the majority-consensus position in current writing, though the underlying evidence is practitioner experience, not controlled studies — treat the *direction* as solid and the *dogma* ("always feature, never layer") as folklore. A pragmatic hybrid — each feature owns its own thin internal layering — is what experienced teams converge on in practice.
Sources: [javapractices: package by feature, not layer](http://www.javapractices.com/topic/TopicAction.do?Id=205) (original 2005 argument); [Package by Layer vs Package by Feature, 2025 writeups](https://jshingler.github.io/blog/2025/10/25/package-by-feature-vs-clean-architecture/) converging on the hybrid.

JTS is already package-by-feature at the top (`voice_daemon.py`, `mux.py`, `camilla.py`, then `voice/`, `tools/`, `web/`, `control/`) — keep it that way. The one drift risk is a feature's public surface leaking (see `__init__ as API` below).

### Hexagonal / ports-and-adapters — and where it's overkill
Ports-and-adapters (a.k.a. hexagonal) says: put the domain logic at the center, define narrow interfaces ("ports") for everything that touches the outside world (hardware, network, disk), and let swappable "adapters" implement them. It earns its cost exactly where you have **a real, swappable boundary with unstable or hard-to-test externals** — e.g., an LLM voice provider, a DSP backend, an ALSA device. It's overkill for CRUD-shaped or single-implementation code: a settings page with one backing store doesn't need a port. Alistair Cockburn coined the pattern for isolating logic from "external agencies"; AWS's own guidance repeats that CRUD-centric, mostly-infrastructure apps don't benefit.
Sources: [Alistair Cockburn, original hexagonal-architecture writeup](https://alistair.cockburn.us/hexagonal-architecture); [AWS Prescriptive Guidance, hexagonal architecture pattern](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/hexagonal-architecture.html) (states the CRUD/overkill case explicitly).

Practical rule for this repo: a port is justified when you can name ≥2 real or plausible adapters (e.g. `voice/` providers, `tools/` LLM tool packs). One implementation forever = no port, just a module.

### Screaming architecture
Robert C. Martin's point: opening the top-level directory tree should announce **what the system does**, not what frameworks it uses — `jasper/voice_daemon.py`, `jasper/mux.py`, `jasper/camilla.py` should be more prominent in the tree than `jasper/utils/` or `jasper/helpers/`. This is a naming/organization discipline, not a technology — treat it as a checklist item during any reorg: does the directory listing read like a smart-speaker's job list, or like a Python-project template?
Source: [Robert C. Martin, "Screaming Architecture" (2011, original)](https://blog.cleancoder.com/uncle-bob/2011/09/30/Screaming-Architecture.html).

### Module boundary rules
- **Acyclic Dependencies Principle (ADP):** the import graph between packages must be a DAG. A cycle means neither package can be built, tested, or understood independently, and a change to one forces reasoning about both. This is the single highest-value structural rule to enforce mechanically (see §2, import-linter).
  Source: [Acyclic dependencies principle](https://en.wikipedia.org/wiki/Acyclic_dependencies_principle) (Martin's original formulation, well-summarized).
- **Stable-Dependencies Principle (SDP):** depend in the direction of stability — a package many others depend on (high afferent coupling) should itself depend on few things (low efferent coupling), because it is expensive to change. Volatile, experimental code should sit at the leaves of the graph, not at its root.
  Source: [Stable Dependencies Principle, package coupling summary](https://link.springer.com/chapter/10.1007/978-1-4842-4119-6_10); original: [Robert Martin, "OO Design Quality Metrics: An Analysis of Dependencies" (1994, PDF)](https://condor.depaul.edu/dmumaugh/OOT/Design-Principles/oodmetrc.pdf).
- **One public surface per package, `__init__.py` as the API:** keep `__init__.py` thin (it runs on every import — no I/O, no heavy setup), and use it plus `__all__` to declare exactly what's public; everything else in the package is implementation detail callers must not reach into directly. This is the Python-native equivalent of a Rust crate's `pub` boundary.
  Source: [Real Python, "What Is Python's `__init__.py` For?"](https://realpython.com/python-init-py/).

### Rust workspace crate boundaries
For a codebase in the 10k–1M LOC range, a **flat** workspace layout (`crates/foo`, `crates/bar`, all one level deep under `crates/`) beats a nested hierarchy — Cargo's crate namespace is flat, so a tree layout just invents a second, inconsistent hierarchy on top of it. rust-analyzer (≈200k LOC) is the reference example. Split crates along real compile/reuse boundaries (a mixer, a final-output owner, a shared protocol crate) rather than by layer; keep common dependency versions pinned once in the workspace root `Cargo.toml`. For ad-hoc build/dev automation, a `cargo xtask` crate beats scattering shell scripts.
Source: [matklad, "Large Rust Workspaces" (2021, primary — matklad is a rust-analyzer author)](https://matklad.github.io/2021/08/22/large-rust-workspaces.html).

Map to this repo: `rust/` (jasper-fanin, jasper-outputd, shared crates) already matches this — verify it's flat under `rust/`, not nested, and that shared types live in one crate consumed by both binaries rather than duplicated.

### Splitting a monolithic daemon
The standard move is decomposition by **bounded context / business capability**, not by technical layer — find the seams where state and failure domains are actually independent, then give each its own process (or at minimum its own module with an enforced boundary) only when that independence buys you something (independent restart, independent failure blast radius, independent deploy cadence). A concrete, well-documented real-world case: libvirt split its monolithic `libvirtd` into per-driver daemons (`virtqemud`, `virtxend`, `virtstoraged`) specifically to shrink blast radius and attack surface — not for aesthetics.
Sources: [Daniel Berrangé, "libvirt: split of the monolithic libvirtd daemon" (2020, primary account from the implementer)](https://www.berrange.com/posts/2020/02/04/libvirt-split-of-the-monolithic-libvirtd-daemon/); DDD bounded-context framing is folklore-by-now-consensus, sourced across [multiple 2025 decomposition writeups](https://itoutposts.com/blog/microservices-decomposition-strategy/).

For JTS specifically: splitting a daemon into a **new OS process** is a big step (added IPC, added restart/ordering complexity) — reserve it for real independent-failure-domain cases (this is presumably why `jasper-fanin`/`jasper-outputd`/CamillaDSP are already separate). Splitting a daemon's *Python module* into smaller modules along the same capability seams is nearly always worth it and much cheaper.

### Where config should live
12-factor's config rule: anything that varies between deployments (secrets, hostnames, feature toggles) belongs outside the codebase, read at runtime — not hardcoded, not baked into per-environment code branches. The complementary, less-cited rule that matters more for a multi-agent codebase is **single owner per setting**: exactly one component reads-and-owns a given piece of config as truth; everything else treats it as derived or asks that owner, rather than every consumer independently re-parsing `os.environ`. This second rule is where most real-world config bugs live (stale caches, two components disagreeing about a value) — it's not explicitly a 12-factor point, it's the practical corollary teams converge on.
Source: [12factor.net, "III. Config"](https://12factor.net/config) (primary, Heroku's original methodology).

JTS's own `AGENTS.md` already encodes this correctly (single-writer env files under `/var/lib/jasper/`, "never cache wizard-owned values from `os.environ`") — this is the right pattern; the failure mode to watch for is a *new* daemon reading a wizard-owned file directly instead of through the owning component's read path.

### File/function size — evidence, not folklore
There is no controlled study proving a specific line-count threshold reduces defects; every number below is a heuristic from experienced practitioners, and they disagree with each other by 20x. What they agree on is the *underlying variable*: a unit should do one thing, and you should be able to hold its purpose in your head. Use size as a **smell detector**, not a hard gate.
- **Linux kernel style:** functions should "fit on one or two screenfuls" and do one thing; the *ceiling is a function of complexity and indentation depth*, not an absolute line count — a long, simple switch statement is fine, a short, deeply-nested function is not.
  Source: [Linux kernel coding style, ch.6, "Functions" (primary, kernel.org)](https://docs.kernel.org/process/coding-style.html).
- **Sandi Metz's rules** (explicitly presented as rules to be *broken with justification*, not law): classes ≤100 lines, methods ≤5 lines, ≤4 params. Useful as a tripwire that forces you to articulate *why* a method grew, not as a merge gate.
  Source: [thoughtbot, "Sandi Metz' Rules For Developers"](https://thoughtbot.com/blog/sandi-metz-rules-for-developers).
- **Martin Fowler's actual position** (frequently misquoted as "keep functions tiny"): length itself isn't the issue — the issue is the **semantic distance between a function's name and its body**. Extract a fragment into a named function whenever reading it costs more effort than reading its name would. A block of code that needs a comment to explain what it does is a extraction candidate regardless of size.
  Source: [Martin Fowler, notes/commentary on function length and Extract Function, *Refactoring*](https://www.informit.com/articles/article.aspx?p=2952392&seqNum=3).
- **Ousterhout's deep-vs-shallow modules** (the most load-bearing idea here): a module's *cost* to the system is its interface, its *benefit* is the functionality it hides behind that interface. A **deep** module (small interface, lots of implementation) is good regardless of its line count; a **shallow** module (a big, chatty interface hiding almost nothing) is bad even if it's tiny. This reframes "file too big" as usually the wrong question — the right question is "does this module's public surface make it easy to use without knowing how it works."
  Source: [John Ousterhout, *A Philosophy of Software Design*, Stanford course PDF (primary lecture material)](https://milkov.tech/assets/psd.pdf).

**Synthesis for this repo:** don't adopt a hard LOC gate. Use radon/lizard complexity thresholds (§2) as the mechanical gate, and use Ousterhout's deep-module test as the human review question: *"if I only read this module's public functions/CLI/HTTP surface, could I use it correctly without reading its body?"* If no, it's shallow and needs a narrower interface — regardless of its size.

## 2. Measuring quality — tools and thresholds

| Concern | Tool (Python / Rust / C) | Threshold heuristic |
|---|---|---|
| Cyclomatic complexity | `radon cc`, `ruff --select C901` (default `max-complexity`=10, same as flake8's `--max-complexity 10`); `lizard` for C and cross-language (default CCN threshold **15**) | ≤10 fine, 11–20 review, >20 refactor |
| Cognitive complexity | SonarSource's metric (definition below) via SonarQube/eslint-plugin-sonarjs-style tools; **not reliably available for Rust** — clippy's `cognitive_complexity` lint exists but is parked in the `restriction` category because its authors state "the true Cognitive Complexity of a method is not something we can calculate" reliably, so treat any Rust cognitive-complexity number as directional only | Sonar's own default flags functions >15 |
| Maintainability Index | `radon mi` | Radon's own docs call MI "a very experimental metric" — use as a coarse smoke alarm only, never a gate |
| Coupling / instability | `import-linter` (contracts: forbidden, independence, **layers**) for Python; `pydeps`/`py_coupling_metrics` for Ca/Ce/instability; `cargo-modules` / Cargo's own crate graph for Rust (Rust already forbids workspace-level crate cycles) | Zero import cycles (ADP) is a hard requirement, not a heuristic; instability `I = Ce/(Ce+Ca))` trending toward 0 for foundational packages, toward 1 for leaf/application packages |
| Duplication | `jscpd` (cross-language, fails CI over a % threshold, tunable via `--min-tokens`/`--min-lines`), `pylint` `R0801` (duplicate-code) | jscpd default project threshold is commonly set to a few percent duplicated lines; a good working number for this repo: red >5%, yellow 2–5%, green <2% |
| Dead code | `vulture` (Python — flags likely-unused code, needs a maintained allowlist for false positives), `deptry` (unused/missing dependencies, Python's rough equivalent of `cargo-udeps`), `cargo-udeps` (nightly-only, unused Cargo.toml deps), `ruff F401`/`F841` (unused import/variable, part of every-commit linting, not a periodic sweep) | F401/F841 should be **zero, always** (cheap, mechanical, already caught pre-commit); vulture/deptry/cargo-udeps run periodically with an explicit, reviewed allowlist file (not scattered `# noqa`) |
| Test coverage | `coverage.py`/`cargo llvm-cov` | Fowler: teams testing "thoughtfully and well" land in the **80s–90s%**; **100% is a red flag**, not a goal — it usually means tests were written to satisfy the number |
| Test-to-code ratio | LOC(tests)/LOC(src) | No universal number; the folklore range is roughly 0.5–1.5x. What actually matters is the *shape*: brittle suites assert on source text, log/error prose, or exact internal call sequences instead of externally observable behavior — this repo's own AGENTS.md rule ("never assert on source text or log/error prose") is already the correct mitigation |
| Mutation testing | `mutmut` (Python), `cargo-mutants` (Rust, zero-config, injects small bugs — swapped operators, defaulted returns — and checks whether tests notice) | A mutation score meaningfully below your line-coverage number means coverage is inflated by tests that execute code without checking its behavior; ThoughtWorks' Radar has flagged `cargo-mutants` as worth adopting specifically because it catches this gap that coverage can't |
| Hotspot / change-risk analysis | `code-maat` (Adam Tornhill's VCS-log analyzer; combine churn from git log with complexity from radon/lizard) | Files that are simultaneously high-churn and high-complexity are the real risk surface — much more actionable than complexity alone, since "complexity only matters if you have to deal with it" |
| Doc drift | no single standard tool; practical proxies: days since last doc edit vs. days since last edit of the code it describes; grep doc prose for symbol/path names that no longer exist in the tree | Treat as a CI check only where cheap (e.g. "does this doc reference a deleted file/flag") — full semantic drift-checking is not worth building for a one-owner project |

Sources: [ruff `complex-structure` (C901) docs](https://docs.astral.sh/ruff/rules/complex-structure/); [lizard, GitHub README](https://github.com/terryyin/lizard); [SonarSource, Cognitive Complexity whitepaper (primary)](https://www.sonarsource.com/docs/CognitiveComplexity.pdf); [clippy `cognitive_complexity` lint status discussion](https://github.com/rust-lang/rust-clippy/issues/14417); [Radon docs, "Introduction to Code Metrics"](https://radon.readthedocs.io/en/latest/intro.html); [Arie van Deursen, "Think Twice Before Using the Maintainability Index" (primary critique, cited widely)](https://avandeursen.com/2014/08/29/think-twice-before-using-the-maintainability-index/); [import-linter docs, contract types](https://import-linter.readthedocs.io/en/latest/contract_types.html); [afferent/efferent coupling & instability, coupling.dev](https://coupling.dev/posts/related-topics/afferent-and-efferent-coupling/); [jscpd](https://jscpd.dev/); [pylint R0801](https://pylint.readthedocs.io/en/latest/user_guide/messages/refactor/duplicate-code.html); [vulture](https://www.x-cmd.com/pkg/vulture/); [cargo-udeps](https://github.com/est31/cargo-udeps); [ruff unused-import (F401)](https://docs.astral.sh/ruff/rules/unused-import/); [Martin Fowler on coverage, via ThoughtWorks summary](https://www.thoughtworks.com/insights/blog/are-test-coverage-metrics-overrated); [mutmut docs](https://mutmut.readthedocs.io/en/latest/index.html); [ThoughtWorks Technology Radar, cargo-mutants entry](https://www.thoughtworks.com/radar/tools/cargo-mutants); [Adam Tornhill, *Your Code as a Crime Scene* — hotspots](http://www.r-5.org/files/books/computers/dev-teams/trenches/Adam_Tornhill-Your_Code_as_a_Crime_Scene-EN.pdf); [Mintlify, "How to Stop Documentation Drift" (doc-drift metrics)](https://www.mintlify.com/library/how-to-stop-documentation-drift).

## 3. Specific to AI-agent-developed codebases

The data is now real and not flattering to the status quo: GitClear's analysis of **211M+ changed lines (2020–2024)** found refactoring's share of changed lines fell from 25% to under 10%, cloned/copy-pasted code rose from 8.3% to 12.3%, and **2024 was the first year on record where copy-paste exceeded refactor-moved code** — with duplicated blocks up roughly 8x in that one year. This is not a hypothetical risk; it is the measured default behavior of agent-assisted teams that don't actively counter it.
Source: [GitClear, "AI Copilot Code Quality: 2025 Data Suggests 4x Growth in Code Clones" (primary research report)](https://www.gitclear.com/ai_assistant_code_quality_2025_research); corroborated by [ThoughtWorks Technology Radar, "Complacency with AI-generated code"](https://www.thoughtworks.com/en-us/radar/techniques/complacency-with-ai-generated-code).

**Known failure modes, with why they happen:**
- **Duplicate helpers.** An agent working in one part of the tree doesn't reliably discover an existing helper elsewhere and writes a new one instead of reusing it — this is a search/context problem, not a competence problem. Mitigation that's actually reported to work: a CLAUDE.md/AGENTS.md that *names* the existing conventions and utility locations up front, so the agent doesn't have to discover them by search.
- **Defensive-guard accumulation.** Agents are trained toward "don't crash," so each turn tends to add another `try/except`, another null-check, another fallback — individually defensible, collectively a fog of guards defending against inputs that can't occur. Compounds silently because no single diff looks wrong.
- **Comment/prose bloat.** Agents over-narrate ("# increment the counter"), which bloats the context every future agent has to read and — worse — drowns out the few comments that carry real information (units, hardware quirks, a why-pointer).
- **Test bloat that pins implementation.** Agents write tests to make the diff look validated, and the fastest test to write is one that asserts on the exact internal shape just produced — which then breaks on any future refactor that doesn't change behavior.
- **Doc sprawl / ADR inflation.** Each session tends to leave a new doc behind rather than updating the existing one, because finding and editing the canonical doc is more work than writing a new one. Left unchecked this produces N slightly-conflicting descriptions of the same subsystem.
Sources: [dev.to, "Debloating The AI-Grown Codebase" — reports the "each turn looks reasonable, the sum doesn't" dynamic](https://dev.to/maximsaplin/debloating-the-ai-grown-codebase-2om); [Medium, "Defensive Code, Dangerous Data" — defensive-code bias in coding assistants](https://medium.com/data-mess/defensive-code-dangerous-data-the-hidden-bias-of-ai-coding-assistants-2336179ff51b); [Simon Willison, "AI should help us produce better code" — duplicate-functionality-over-time framing](https://simonwillison.net/guides/agentic-engineering-patterns/better-code/).

**Mitigations people actually recommend, that are checkable, not just aspirational:**
1. **A short, canonical AGENTS.md/CLAUDE.md** naming existing modules/utilities/conventions, kept under ~200–300 lines — consensus across sources is that shorter and more concrete beats longer and more thorough; growth should come from real friction hit twice, not anticipated problems.
   Sources: [Anthropic, "Effective context engineering for AI agents" (primary)](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents); community consensus on the ~200–300 line ceiling, e.g. [HumanLayer, "Writing a good CLAUDE.md"](https://www.humanlayer.dev/blog/writing-a-good-claude-md).
2. **Architecture tests enforced in CI**, not just documented convention — `import-linter` layer/forbidden-modules contracts are the concrete Python mechanism; this is "the only enforcement Python's runtime will never give you." The equivalent for Rust is largely free: Cargo itself refuses workspace crate cycles.
   Source: [Kokonatt, "Enforcing Modular Boundaries with Import Linter"](https://www.kokonatt.com/blog/modular-boundaries-import-linter/).
3. **One home per concern, enforced by structure, not memory** — a registry/dispatch table (tool packs, cue registry, voice providers) that makes "where does X live" a lookup rather than a search, and makes a second implementation visually obvious as a second registry entry rather than invisible as a second file somewhere else in the tree. JTS already does this (`jasper/cues/registry.py`, `jasper/tools/`) — the mitigation here is *keeping every new concern flowing through an existing registry* rather than agents inventing parallel dispatch.
4. **Periodic consolidation passes** rather than continuous perfectionism — since duplication and guard-accumulation are a compounding-turns problem, the fix is a recurring pass (this repo's `/code-review`, `/simplify`, and periodic deep-audit skill) rather than trying to prevent every instance at commit time.
5. **Budgets, stated as numbers, for things that silently grow** (LOC, config knobs, ADR count, doc files) — not because the number itself is sacred, but because a stated budget forces an explicit consolidation decision instead of unbounded accretion. This is a light mitigation, closer to folklore than proven practice, but it's cheap and directly addresses the measured failure mode above.

## 4. Resilience and observability for a small fleet of constrained-hardware daemons

What's proportionate for **one owner, a handful of Pis, 1GB–415MB RAM**, vs. what's SRE-team overkill:

**Worth doing (cheap, directly addresses real failure modes):**
- **Structured event logs** (`event=wake_timeout`, `event=camilla_reconnect`, key=value or JSON, not prose) — the payoff isn't fancy tooling, it's that `grep`/`jq` over `journalctl` becomes reliable evidence instead of prose-parsing. This is already AGENTS.md's own "evidence first" doctrine.
- **A `/state` or health endpoint per long-running daemon** exposing current mode, last-error, last-successful-heartbeat — cheap to add, and it's the thing "verify at the user's surface, not upstream config" actually depends on.
- **systemd's own watchdog (`WatchdogSec` + `sd_notify(WATCHDOG=1)`)** for detecting a hung-but-alive process, tied to a *real* internal liveness signal (a queue making progress, a loop tick) — not an unconditional heartbeat, which defeats the purpose entirely.
  Source: [oneuptime.com, systemd watchdog configuration guide](https://oneuptime.com/blog/post/2026-03-02-how-to-configure-systemd-watchdog-for-service-health-checks-on-ubuntu/view); the "don't heartbeat unconditionally" caveat is the whole point of the mechanism, repeated across [systemd watchdog best-practice writeups](https://oneuptime.com/blog/post/2026-03-04-set-up-systemd-watchdog-monitoring-for-critical-services/view).
- **`Restart=on-failure` + `StartLimitBurst`/`StartLimitIntervalSec`** — restart-loop detection is close to free with systemd and prevents a crash-loop from burning the Pi's limited resources; systemd marks the unit failed (not stuck restarting forever) once the burst limit is hit within the interval.
- **Bounded queues everywhere audio/events flow**, with an explicit drop-or-reject policy at capacity (the "leaky bucket" pattern) — an unbounded queue on a 1GB Pi is a slow-motion OOM, not a safety margin.
  Source: [SRE School, "What is Leaky bucket?"](https://sreschool.com/blog/leaky-bucket/).
- **A simple failure budget concept**, informally: "how many wake failures / restarts per day before this is a bug, not noise" — you don't need formal SLOs, but naming the threshold turns "seems flaky lately" into a checkable fact.

**Overkill for this project (skip unless a real incident justifies it):**
- Full SLO/error-budget tooling, dashboards, or a metrics time-series database — proportionate for a team operating a fleet at scale, not a one-owner hobby system with a handful of Pis you can SSH into.
- A general-purpose observability stack (Honeycomb/Datadog-style tracing) — the value of distributed tracing is correlating spans across many services under concurrent load; a single Pi's `journalctl` plus a `/state` endpoint already gives equivalent evidence for less machinery.
- External synthetic monitoring / uptime-checking services — there's no SLA to protect and no on-call to page; a periodic self-check plus AGENTS.md's existing "no silent deafness" cue requirement already covers the actually-bad failure mode (the user can't tell it's broken).
  Source: [Honeycomb / general observability-engineering writeups explicitly note the setup+expertise cost is only justified when a team has the headcount for it](https://www.honeycomb.io/resources/getting-started/what-is-observability-engineering) — the inverse argument (skip it below that scale) is this document's own extrapolation, not a directly stated claim; treat it as reasoned opinion, not cited fact.

## 5. Quality rubric (one page, mechanical, red/yellow/green)

Grade at the **package/crate/daemon** level, not the whole repo at once — a repo-wide single score hides exactly the local hotspots that matter.

| # | Attribute | Definition | How to measure here (Python + Rust + bash) | Red | Yellow | Green |
|---|---|---|---|---|---|---|
| 1 | Function complexity | How many independent paths through one function | `radon cc` / `ruff --select C901` (Python), `lizard` (C, Rust) | any function >20 | 11–20 | ≤10 |
| 2 | Module depth | Simple interface hiding real functionality (Ousterhout) | manual: can you use the module's public functions/CLI without reading its body? | interface as complex as the implementation | some leakage of internals into the public surface | small public surface, rich implementation |
| 3 | Import-graph acyclicity | No cycles in the dependency graph (ADP) | `import-linter` contract in CI (Python); Cargo enforces it for crates; check module-level cycles in Rust/C manually | any cycle present | cycle exists but is contained + tracked | zero cycles, contract enforced in CI |
| 4 | Coupling direction | Stable/foundational code doesn't depend on volatile code (SDP) | afferent/efferent count via `pydeps`/`cargo-modules`; eyeball which way arrows point between `jasper/` core and `web/`/`cli/` | core imports from a leaf/experimental module | occasional, justified exception | dependencies flow from volatile → stable only |
| 5 | Duplication | Near-identical code blocks across files | `jscpd` / `pylint R0801` in CI | >5% duplicated lines, or any duplicated *safety-relevant* block (volume clamp, deploy guard) | 2–5%, no safety-relevant hits | <2%, zero safety-relevant hits |
| 6 | Dead code | Code/deps nothing calls or needs | `vulture` + `deptry` (Python), `cargo-udeps` (Rust), `ruff F401/F841` every commit | large unreviewed findings list, or a stale, unmaintained allowlist | small allowlist, reviewed each quarter | F401/F841 zero always; vulture/deptry/udeps clean or explicitly justified |
| 7 | Test-to-behavior fit | Tests pin externally observable behavior, not source text/log prose/internal shape | grep test files for string/log-prose assertions; spot-check after a pure refactor — do unrelated tests break? | tests assert on log/error text or exact internal structure | occasional overreach, being cleaned up | tests assert only on types/codes/structured fields |
| 8 | Test truth (mutation score) | Do the tests actually fail when behavior breaks? | `mutmut` (Python) / `cargo-mutants` (Rust) on non-negotiable-tier modules at minimum | mutation score <50% where line coverage is high (coverage is theater) | 50–70% | >70%, or gap between coverage% and mutation score is small |
| 9 | Hotspot risk | High git churn **and** high complexity in the same file | `git log --stat` churn crossed with `radon cc`/`lizard` complexity per file | top-churn files are also top-complexity and under-tested | one of the two, being watched | high-churn files are simple, or high-complexity files are stable/untouched |
