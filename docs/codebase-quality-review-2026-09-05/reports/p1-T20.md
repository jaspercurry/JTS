# T20 — rust/jasper-outputd (20 files, 17,751 LOC)

## A. Mandate and verdict

**Mandate:** own the final electrical edge — read CamillaDSP's post-DSP program off the SHM
ring, write it to the DAC, publish bounded health counters and the AEC reference taps.

**Verdict: one coherent system with two bolted-on tenants.** The DAC-write spine
(`main::run_alsa` → `alsa_backend` → `shm_ring_source` → `types`/`mixer`/`content_fill`) is
genuinely one thing and is the best-engineered code I read in the tile. Bolted on: (1) a
**second full TTS daemon** (`tts.rs` + `core.rs` + `assistant_source.rs` + `ledger.rs`,
~2,900 LOC) that only runs on a bonded member and is a fork of jasper-fanin's; (2) a
**second full observability daemon** (`state.rs`, 3,830 LOC) that is a fork of jasper-fanin's
`state.rs` down to the constant names. Both forks are re-implementations, not shared code.

Numbers: prod 10,474 / test 7,215 (**41 % test LOC**, healthy); 10 functions > 100 LOC;
3,956 comment lines (22 %); **0 lines of `jasper-host-clock`'s 3,804-line lib are consumed
here** — outputd does not depend on that crate at all (Cargo.toml has no entry; only
jasper-fanin does). It consumes `jasper-clock` narrowly and well: `Dll` + `DllConfig` +
`DllSnapshot` only, ~10 of the crate's 849 lines' worth of API, all inside `dac_clock.rs`.

**Wireless-subwoofer deletion (#4079 / commit 3303f8827): clean, no leftovers in this tile.**
No `SUB_HZ`/`HP_HZ`/`Lr4*`/`Sub` pick/`main_highpass_hz` anywhere in `rust/jasper-outputd`;
`ChannelPick` is exactly `stereo|left|right|mono`; the only surviving mentions repo-wide are
ADR-0236 (correct, it records the deletion) and a stale work-prompt in
`docs/ux-audit-2026-09-03/PROMPT-subwoofer-deletion.md` (cross-tile).

**Earns-its-keep (tried to cut, could not):**
- `dac_clock.rs` + `aec_clock.rs` side by side — different clock pairs, and `aec_clock.rs:51-63`
  documents the empirical reason the DLL cannot replace least-squares here (mid-range ppm collapse).
- `types.rs`'s three narrow/widen wrappers — `narrow_period_i24_le` genuinely cannot be a width
  parameter on `narrow_period` (its output element is a byte), and
  `narrow_period_is_wired_to_the_rounding_primitive_not_the_truncating_one` is the only test in
  the tree that catches a half-LSB bias at the speaker edge.
- `content_fill.rs` — 97 prod lines that answer a question no cumulative counter can ("deaf right now").
- **Gain audit (extra focus):** every gain on the **content** path is ≤ unity and enforced at parse.
  `apply_linear_gain` (`main.rs:873`) is applied twice — the pair trim (bounded to `[-24, 0]` dB by
  `state.rs:368-382` and `config.rs:557-570`) and the program duck (`config.rs:651-657` bails on
  `> 0`). Neither can boost. The **assistant** path (`assistant_source.rs:222-232`) *can* exceed
  unity and sits downstream of CamillaDSP's `volume_limit=0.0`, but is bounded by
  `peak_cap_gain_db = max_peak_dbfs − source_peak_dbfs` (`jasper-tts-protocol/src/loudness.rs:446`)
  and by `mix_saturating`'s i64-accumulator clamp, and it honours `canonical_db` through
  `VolumeContext` — so no unbounded post-DSP boost exists. No non-negotiable breach found.
- **RT safety of the output thread:** better than I expected. Every lock the playout thread can
  take is `try_lock` (`state.rs:669`, `core.rs:424`); the `dac_narrow_buf`/`dac_pack_buf`/
  `s16_scratch`/`narrow_staging` allocations are all open-time and conditional on the width that
  needs them; the UDP tap is nonblocking and drops with a counter (`main.rs:1035-1043`). Two real
  residues: `ChipRefDownsampler::process` allocates a `Vec` per period (`main.rs:1146-1155` —
  already documented as a known exception, chip-AEC boxes only), and `AssistantSource` frees a
  queued reply's `Vec<i16>` **on the playout thread** when a segment drains
  (`assistant_source.rs:288-307`), which under `panic = "abort"` + `mlockall` is a `free()` of up
  to a 2-second buffer inside the DAC period. Both are bonded-member-only. Worth a note, not a rewrite.

**Smaller items not ranked:** `main.rs:239,745` — `notify_systemd("WATCHDOG=1")?` kills the daemon
on a transient notify failure (fanin logs and continues). `main.rs:383-384,720-731` — `reference_buf`
is allocated and the stereo fold is computed every period even when no tap is armed, while
`ReferenceSideOutputs::new` (`main.rs:918-931`) goes to documented lengths to avoid exactly that
allocation. `main.rs:356-358` `state_counters` and `alsa_backend.rs:1424-1433` `verify_dac_format`
are one-line pass-throughs. `main.rs:735-741` and `main.rs:1617-1621` spell the same
`event=outputd.once` format string twice. `dac_content.rs:361-364` logs `read_failed` on every
failed read with no once-per-episode guard, unlike its `logged_first_starvation` sibling.
`dac_clock.rs:138` takes `_period_frames` "for constructor symmetry" — an always-unused param.
`config.rs:962-970` `env_bool` silently reads an unrecognised value as `false` (mitigated: the
vocabulary is mirrored and pinned in `jasper/fanin_coupling.py:385`). `tts.rs:238-276` spawns an
uncapped thread per TTS client with no idle timeout, each pinning 512 KiB under `mlockall`.
`crate::mixer::gain_db_to_linear` (`tts.rs:68`) and `crate::loudness::gain_db_to_linear`
(`assistant_source.rs:31`) are two local doors to one re-exported symbol.

## D. If I could do one thing to this tile

Stop forking jasper-fanin. `json_string`, `push_kv_*`, `EXIT_CONFIG`/`ConfigClassError`,
`lock_memory`, `HELPER_STACK_BYTES`, the ring-attach classifier, and the whole TTS server shell
are the same code twice — and the fork has already drifted somewhere it matters (outputd silently
lost fanin's TTS protocol-error and stale-command counters). One shared daemon crate plus moving
the TTS server half into `jasper-tts-protocol` removes ~450 LOC and closes that class of drift.
